# E0401: mismatched types

Every expression has a type, and Ki checks it against the type that its place expects: the annotation
of a `let`, the return type of a function, the parameter of a call, the other branch of an `if`, the
operand of an operator. When the two are different types, this is the error. Ki converts nothing by
itself, so an `Int` is never taken for a `Bool` or the other way round, and there is no edit that the
compiler could propose, except for one mistake: a number written without a point where a `Float` is
expected (`printFloat(2)`), for which the edit writes it with one (`2.0`), the same number. An `Int`
above 2^53 may have no `Float` of its own (`9007199254740993` would become `9007199254740992.0`), and
then there is no edit: the number to write is for the author to choose.

The primary label is on the expression that was found and says ``expected `X`, found `Y` ``. A secondary
label points at the place that made `X` the expected type, and what it says depends on that place; each
example below shows one. Function types are compared part by part, and the label writes the two
types, such as `(Int) -> Bool` and `(Int) -> Int`, whichever part differs. A type that takes more than
256 bytes to write is cut there and ends in `…`.

## Erroneous example

```ki erroneous
fn main() { let x: Bool = 1 }
```

The annotation says that `x` is a `Bool` and the initializer is an `Int`. The label on the `1` says
``expected `Bool`, found `Int` ``, and the secondary label on the annotation says `expected because of
this annotation`.

## Corrected

```ki corrected
fn main() { let x: Bool = true }
```

## Erroneous example

```ki erroneous
fn main() { printFloat(2) }
```

`printFloat` takes a `Float` and `2` is an `Int`. The label on the `2` says ``expected `Float`, found `Int` ``
and the help says to write the number as a `Float`: the edit writes `2.0`. Only a literal has it: for a
variable that holds an `Int`, whether to convert it with `toFloat` or to change its type is for the
author to say.

## Corrected

```ki corrected
fn main() { printFloat(2.0) }
```

## Erroneous example

```ki erroneous
fn f() -> Int { true }
fn main() { }
```

The last expression of a body is what the function returns, and it must have the return type. The
label on the `true` says ``expected `Int`, found `Bool` ``, and the secondary label on the return type
says `expected because of the return type`.

## Corrected

```ki corrected
fn f() -> Int { 1 }
fn main() { }
```

## Erroneous example

```ki erroneous
fn f() { 1 }
fn main() { f() }
```

A function with no `->` returns `()`, so its last expression has to be `()`. Here it is an `Int`, and
the secondary label sits on the name of the function, because there is no return type to point at.
This mistake comes with a help line of its own (the other one on this page is for a number that is to be a
`Float`): ``this value is unused: bind it with `let name = …`, or return it from the function``. The compiler
does not offer an edit, because what to call the variable, and whether the value is to be bound or returned,
is for the author to say. The second half is left out where returning the value would not help: in `main`,
whose type has to be `() -> ()` (see E0404), and at the end of an `if` that has no `else`.

## Corrected

```ki corrected
fn f() -> Int { 1 }
fn main() { }
```

## Erroneous example

```ki erroneous
fn fib(n: Int) -> Int { if n < 2 { n } else { fib(n - 1) + fib(n - 2) } }
fn main() { fib(10) }
```

The same mistake in `main`, which is where it is most likely: `main` returns `()`, and `fib(10)` is an
`Int`. The help here offers only the first half, ``this value is unused: bind it with `let name = …` ``,
because returning the value would give `main` a return type, and that is E0404.

## Corrected

```ki corrected
fn fib(n: Int) -> Int { if n < 2 { n } else { fib(n - 1) + fib(n - 2) } }
fn main() { print(fib(10)) }
```

## Erroneous example

```ki erroneous
fn f(a: Int) {}
fn main() { f(true) }
```

An argument is checked against the type of its parameter. The label on the `true` says
``expected `Int`, found `Bool` ``, and the secondary label on the parameter says
`the parameter is declared here`.

## Corrected

```ki corrected
fn f(a: Int) {}
fn main() { f(1) }
```

## Erroneous example

```ki erroneous
fn main() { let x = if true { 1 } else { false } }
```

Both branches of an `if` that is used as a value have the same type, and the `then` branch is the one
that decides it. The label on the `false` says ``expected `Int`, found `Bool` ``, and the secondary label
on the `1` says ``the other branch has type `Int` ``. The exception is a `Float`: where one is expected
(`fn f(b: Bool) -> Float { if b { 1 } else { 2.5 } }`) each branch is compared with it, and the error is on
the `1`, with the edit that writes `1.0`, because the `2.5` is not the one that is wrong.

## Corrected

```ki corrected
fn main() { let x = if true { 1 } else { 2 } }
```

## Erroneous example

```ki erroneous
fn main() { if 1 { } }
```

The condition of an `if` must be a `Bool`, and Ki does not take a number for a truth value. The label on
the `1` says ``expected `Bool`, found `Int` ``. There is no secondary label, because no other place
explains the expectation; the note says the rule: ``an `if` condition must be `Bool` ``.

## Corrected

```ki corrected
fn main() { if true { } }
```

## Erroneous example

```ki erroneous
fn main() { let b = true && 1 }
```

Each operator wants operands of one type: `&&` and `||` want `Bool`, `%` wants `Int`, and `+ - * /` and
the ordering comparisons `< <= > >=` want two `Int` or two `Float`. The label on the `1` says
``expected `Bool`, found `Int` ``, and the secondary label on the operator says
`` `&&` expects `Bool` operands ``.

## Corrected

```ki corrected
fn main() { let b = true && false }
```

## Erroneous example

```ki erroneous
fn f() {}
fn g() -> Bool { f == f }
fn main() { }
```

`==` and `!=` compare two values of one type, and that type has to be `Int`, `Bool` or `Float`: a
function cannot be compared, and neither can `()`. The label is on the left operand and says
``expected `Int`, `Bool` or `Float`, found `() -> ()` ``. There is no secondary label, because no other
place in the program explains the rule; the note says it: `` `==` works on `Int`, `Bool` and `Float` here ``.
That is the only error of the comparison: the right operand is not compared with a function, because `==`
does not expect one there. When the left operand is an `Int`, a `Bool` or a `Float`, the right operand is
checked against it, so `1 == true` is an ordinary mismatch, with the secondary label
`` `==` expects `Int` operands `` on the operator.

## Corrected

```ki corrected
fn f() -> Int { 1 }
fn g() -> Bool { f() == f() }
fn main() { }
```

## Erroneous example

```ki erroneous
fn f() {}
fn same(x, y) -> Bool { x == y }
fn main() { let b = same(f, f) }
```

A parameter with no annotation has no type until something says what it is, and here it is the call in
`main`. The comparison in `same` is judged after the whole program has been read, so the error is the
same whichever of the two functions is written first: the label on the `x` says
``expected `Int`, `Bool` or `Float`, found `() -> ()` ``. A parameter that nothing ever types is not an
error. Such a parameter keeps a type variable, in the signature of `same` and in the type of each operand of
`==`. When a later pass has to choose between comparing `Int`s, `Bool`s and `Float`s for it, it chooses `Int`.
That cannot change what a program does: a value whose type nothing knows never exists, because `main`
takes no parameters, so every value starts as a literal, a function or the result of a function of the
prelude.

## Corrected

```ki corrected
fn f() {}
fn same(x, y) -> Bool { x == y }
fn main() { let b = same(1, 2) }
```

## Erroneous example

```ki erroneous
fn main() { let r = 1 + 2.0 }
```

Ki converts nothing between `Int` and `Float`, and the left operand says which of the two the operator
works on: the label on the `2.0` says ``expected `Int`, found `Float` ``, and the secondary label on the
`+` says `` `+` expects `Int` operands ``. With a `Float` on the left it is the other way round. Write the
conversion: `toFloat(1) + 2.0`.

## Corrected

```ki corrected
fn main() { let r = toFloat(1) + 2.0 }
```

## Erroneous example

```ki erroneous
fn main() { let r = true + 1 }
```

`+ - * /`, the four orderings and the negation work on `Int` and on `Float`. When the left operand is
neither, that is the one mistake, on the left operand, and nothing is said about the right one: the label
says ``expected `Int` or `Float`, found `Bool` `` and the note says `` `+` works on `Int` and `Float` here ``,
with no secondary label, because no other place explains the rule.

## Corrected

```ki corrected
fn main() { let r = 2 + 1 }
```

## Erroneous example

```ki erroneous
fn main() { let r = 7.5 % 2.0 }
```

`%` is only for `Int`. The one error is on the left operand, ``expected `Int`, found `Float` ``, with the
secondary label `` `%` expects `Int` operands `` on the operator: the right operand is not compared with
`Int`, and the result has no type to disagree with the place where it is used.

## Corrected

```ki corrected
fn main() { let r = 7 % 2 }
```

## Erroneous example

```ki erroneous
fn f(x) { let y = x + x }
fn main() { f(true) }
```

An operator on a parameter that has no annotation, `%` included, waits for the rest of the program to say
what the parameter is, as `==` does, so the error is the same whichever of the two functions is written
first: the label on the first `x` says ``expected `Int` or `Float`, found `Bool` ``. A parameter that
nothing types is not an error, and a later pass takes it for an `Int`.

## Corrected

```ki corrected
fn f(x) { let y = x + x }
fn main() { f(1.5) }
```
