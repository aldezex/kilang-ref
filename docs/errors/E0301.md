# E0301: unknown name

A name is used that no definition, parameter or `let` in scope provides. Ki looks a name up
in the innermost scope first, then in the enclosing scopes, then among the top-level
definitions of the module and the public names of the prelude. A `let` is visible only
after its own statement, so it cannot name itself in its initializer.

A function whose signature has a syntax error still counts as defined: a call to it is not
reported here, because the compiler has already reported the error in the signature.

In a record literal, a field that is only a name, `Point { xx }`, is also the variable that gives its value,
so writing the closest name over it would change the field too, and the edit allows for that. When `xx` is a field of
the record (or the compiler cannot tell what the record is), only the variable is wrong, and the edit keeps
the field and gives it the closest name: with `type P2 { xx: Int }` and a parameter `x`, it is `P2 { xx: x }`.
When `xx` is not a field either, the name is wrong twice (E0409 says so, with no edit of its own), and the one
edit that this error offers writes the closest name alone, `Point { x }`, which mends both names if that is a
variable and also a field that the literal does not give already (a function is not what a pun reads). If it is
not, there is no edit: `size: sizes` would mend them, but the field would have to be chosen too, and that is the
question that E0409 asks.

## Erroneous example

```ki erroneous
fn main() { prnt(1) }
```

`prnt` is not defined anywhere, so the name cannot be resolved. The compiler suggests the
closest name it knows and offers to write it for you.

## Corrected

```ki corrected
fn main() { print(1) }
```

## Erroneous example

```ki erroneous
fn main() { let x = x }
```

The `x` in the initializer is not the variable that this `let` is binding: the variable exists
only after the statement. The compiler points at the `let` and explains the rule.

## Corrected

```ki corrected
fn main() { let x = 1 }
```
