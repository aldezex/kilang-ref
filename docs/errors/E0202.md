# E0202: unclosed delimiter

A `{`, `(` or `[` was opened and the file ended before its closing partner came. The compiler
points at the delimiter that is never closed, not at the end of the file where it noticed, and
suggests the closing one.

## Erroneous example

```ki erroneous
fn main() {
  print(1)
```

The `{` of the function is never closed. The compiler offers to write the `}` at the end of the file.
If the file ends inside a comment that nothing closes (a `//` comment with no line break after it, or a
`/*` with no `*/`), the end of the file is part of that comment, so the compiler offers the `}` right
after the last token instead, in front of the comment.

The compiler gives the help and no edit when the place where the `}` would be written is inside a
string or a character literal that is never closed, or at its very end: there the `}` would be part
of the literal and would close nothing. That place is the end of the file when the literal runs to it
(there is no line break after it) or, when the file ends in a comment, the end of the last token read,
which can be the literal itself or the code of a `${` in it that is still open. Close the string first,
as E0110 says (or the character, as E0108 says), and check again.

The compiler cannot tell where the `}` was forgotten. If it is missing in the middle of the file, say
at the end of a function that other functions follow, the block does not end at the next `fn`, because
the language allows a function inside a block. The lines that begin the items after it are each
reported with E0201, and the E0202 is only found at the end of the file, where the edit goes. So the
edit does not repair the file: those E0201 stay until the `}` is written where the function ends.

## Corrected

```ki corrected
fn main() {
  print(1)
}
```
